# Runbook: обратная разработка требований (v3, запуск через runner)

Пайплайн разделён на два слоя:

* **Детерминированный слой** (`../runner.py`, `../checks/`, `../schemas/`) —
  оркестрация, подстановка переменных, схемная валидация, механические
  проверки, отчёты. Всё, что решается grep'ом, диффом и пересчётом.
* **Смысловой слой** — промпты этого каталога. Они выполняют то, что требует
  чтения смысла кода: извлечение правил и домена, синтез, формулировки.

Паттерн взаимодействия: LLM порождает → код проверяет → LLM правит по тексту
конкретной ошибки. Гейт — всегда код. Ретраев два, затем эскалация человеку.

## Запуск

```sh
cd req-reverse
# заполните config.yaml: repo.path, repo.name, agent.command
python runner.py --config config.yaml          # этапы 0–7 и 90
python runner.py --stages 0,1,4                # выборочно
python runner.py --force                       # перегенерация валидных выходов
python runner.py --dry-run                     # план без вызова агента
```

Runner сам подставляет переменные в промпты, выдаёт модулям блоки ID,
маскирует секреты в артефактах, гоняет схемы и проверки после каждого этапа
и пишет `workspace/run.log` + `workspace/run_summary.md`. Повторный запуск
идемпотентен: этапы с валидным выходом пропускаются.

## Ярусная глубина реверса

Полная экстракция по холодным зонам даёт дорогие спеки, устаревающие до
первого использования — baseline обязателен там, где случается propose, а не
по площадям. Карта глубины задаётся в `config.yaml → tiers` по каталогам /
capability:

| Ярус | Этапы | Назначение |
|---|---|---|
| `L0` | 0–1 | «оглавление системы» по всему ландшафту, дёшево |
| `L1` | + 2–3 | зоны интеграций (доменная модель + контракты) |
| `L2` | полный прогон (4+ и валидация) | горячие capability: изменения ближайших кварталов, регуляторика |

Умолчание для путей вне карты — `L0` (без секции `tiers` всё идёт как `L2` —
поведение базовой постановки). План строится с учётом яруса: этапы 4+ — только
для зон L2, этапы 2–3 — для L1 и выше; этап 4 фан-аутится только по модулям L2.

В холодную зону впервые пришёл change — зона поднимается по требованию:

```sh
python runner.py --raise-tier src/payments/ L2
```

Команда сохраняет поднятие в `workspace/tiers.yaml` (поверх карты config) и
догоняет недостающие этапы; готовые артефакты нижних ярусов не
перегенерируются — идемпотентность распространяется на ярусы.

## Переменные прогона

Подставляются runner'ом автоматически (руками — только если запускаете промпт
без runner, например для отладки):

| Переменная | Откуда берётся | Что это |
|---|---|---|
| `{REPO_PATH}` | `config.yaml: repo.path` | корень анализируемого репозитория |
| `{REPO_NAME}` | `config.yaml: repo.name` | короткое имя, префикс ID правил |
| `{WS}` | `config.yaml: workspace` | каталог артефактов |
| `{MODULE_PATH}` | план из инвентаризации этапа 0 | модуль для этапов 1 и 4 |
| `{OUT_FILE}`, `{OUT_FILE_*}` | runner | путь артефакта задачи |
| `{ID_START}` | `checks/id_allocator.py` | начало блока ID модуля (этап 4) |
| `{LAYER1_REPORT}` | `checks/evidence_binding.py` | отчёт слоя 1 (этап 90) |

Каталог `{WS}/_scratch/` создаётся runner'ом: туда агент складывает рабочие
скрипты и черновики, чтобы они не смешивались с артефактами.

## Порядок этапов

| № | Промпт | Вход | Выход |
|---|---|---|---|
| 0 | `00_inventory.md` | дерево репозитория, манифесты, README | `{WS}/inventory/{REPO_NAME}.yaml` |
| 1 | `01_module_map.md` | один модуль за запуск | `{WS}/extracts/{REPO_NAME}/modules/<модуль>.yaml` |
| 2 | `02_domain.md` | модели, миграции, схемы | `{WS}/extracts/{REPO_NAME}/domain.yaml` |
| 3 | `03_interface.md` | роутеры/контроллеры либо CLI | `api.openapi.yaml` или `api.cli.yaml` |
| 4 | `04_rules.md` | один модуль за запуск | `{WS}/extracts/{REPO_NAME}/rules/<модуль>.yaml` |
| 5 | `05_flows.md` | все экстракты 0–4 | `{WS}/integration/flows.md` |
| 6 | `06_stories.md` | rules + flows | `{WS}/final/stories.md` |
| 7 | `07_srs.md` | все артефакты | `{WS}/final/SRS.md`, `traceability.csv` |
| 8 | `08_final_package.md` | всё вместе | финальный пакет (заменяет 6+7 при одном прогоне) |
| 89 | `89_docs_instructions.md` | документация проекта | `{WS}/validation/docs_instructions.md` |
| 90 | `90_validate_batch.md` | rules + код + отчёт слоя 1 | `{WS}/validation/validation.csv`, вердикт по порогу |
| 91 | `91_validate_one.md` | одно требование | вердикт одной строкой (точечная перепроверка) |
| 92 | `92_inverse_verify.md` | ТОЛЬКО statement'ы правил capability | `{WS}/validation/inverse/<модуль>.predictions.yaml` |
| 09 | `09_openspec_export.md` | синтез этапов 5–7 | `openspec/specs/` — живая specs library |
| 10 | `10_incremental_sync.md` | диф кода от среза | точечная синхронизация базы знаний |

Этапы 1 и 4 идут **по одному модулю на запуск** — требование исходных промптов:
модуль подаётся целиком, чтобы правила не выдумывались по обрывкам. Фан-аут и
фильтрацию модулей (тесты, вендоринг, генерённый код) выполняет runner.

Механические проверки после этапов (гейт кода):

| После этапа | Проверки |
|---|---|
| 0–3 | JSON Schema артефакта |
| 4 | схема + `evidence_binding` (слой 1) + коллизии ID |
| 7 | `completeness`: правила ↔ истории ↔ трассировка, колонки CSV |
| перед 90 | `evidence_binding` повторно; отчёт слоя 1 передаётся агенту |
| 90 | схема validation.csv + порог приёмки |
| 92 | схема предсказаний; затем `inverse_match`: нормализованный поиск предсказанного в исходниках |
| конец прогона | `coverage`: покрытие ветвлений правилами (полнота) |

### Этап 92 — инверсная верификация (подключаемый)

Третий механизм валидации для систем, где слой 2 (исполнение) недоступен:
корпоративную систему не поднять в песочнице. Верификация «в обратную
сторону» (идея spec-gen/OpenLore): не «спека подтверждается кодом», а «по
спеке предсказывается код, предсказание сверяется с фактом».

Контур: runner готовит файл ТОЛЬКО из `statement`'ов правил capability (без
`evidence` и `source` — иначе предсказание вырождается в пересказ цитат);
модель предсказывает проверки, сообщения, пороги и расположение;
`checks/inverse_match.py` механически ищет предсказанное в исходниках
(нормализация регистра и пробелов, плейсхолдеры чисел `<N>`).

Интерпретация: низкая доля по правилу → из формулировки не восстанавливается
поведение → кандидат на возврат в этап 4. Метрика **дополняет** этап 90, а не
заменяет его. Включение: `config.yaml → validation.inverse: true`. Пороги
приёмки в v3 не калибруются — этап только собирает статистику
(`workspace/reports/inverse_match.md`); калибровка — v3.1.

## Настройка CLI-агента

Комплект **не привязан ни к какому LLM и ни к какому CLI**: runner знает
только шаблон команды из `config.yaml → agent.command` и код возврата;
прямых обращений к API в коде нет. Подставьте любой инструмент, который
выполняет контракт:

1. **работает без интерактива** (не ждёт подтверждений в терминале);
2. **сам читает файлы репозитория и сам пишет артефакт** по пути из промпта;
3. **завершается с кодом 0** при успехе.

Признак успеха для runner — код возврата 0 плюс появившийся файл, прошедший
схему и проверки. Незаполненная команда останавливает прогон сразу, с
подсказкой, — ретраи не тратятся.

Способы передачи промпта (подстановка по-токенно — кавычки и переносы в
тексте промпта не ломают разбор команды):

| Плейсхолдер / опция | Что подставляется | Когда использовать |
|---|---|---|
| `{prompt_text}` | текст готового промпта одним аргументом argv | CLI вида `<агент> -p <текст>` |
| `{prompt_file}` | путь к файлу с промптом | CLI, принимающие файл |
| `stdin: true` | текст промпта на stdin | CLI, читающие пайп |

Дополнительно доступны `{model}` (значение из `models` для этапа, передаётся
как есть — уровни или имена моделей вашего вендора), `{out_file}`, `{workdir}`.
Если агент печатает статистику токенов в stdout, задайте `agent.metrics_regex`
(одна группа захвата числа) — сводка прогона посчитает стоимость.

### Если CLI требует подтверждений (нет неинтерактивного режима)

Подтверждения в корпоративных CLI обычно вызывают **инструментальные
действия** агента: запись файлов, запуск команд, иногда чтение. Порядок
действий:

1. Сначала поищите штатный режим CI/headless у самого CLI: флаг
   автоподтверждения, профиль политики, allowlist инструментов — это
   правильное место решения, и обычно его выдают под задачи автоматизации.
2. Если записи запрещены, а чтение свободно — `agent.mode: stdout`: агент
   ничего не пишет, артефакты выводит в stdout FILE-блоками, файлы записывает
   runner. Runner принимает блоки **только по ожидаемым путям задачи** —
   посторонний путь логируется и игнорируется.
3. Если подтверждений требует любой инструмент — `agent.mode: text`: агент
   работает вообще без инструментов. Входы каждого этапа (исходники модуля,
   готовые артефакты, шаблоны) вкладывает в промпт детерминированный слой
   INPUT-блоками; бюджет вложений — `agent.max_inline_kb` (переполнение —
   эскалация с подсказкой, входы не обрезаются молча: правило v2 «модуль
   подаётся целиком» сохраняется). Ограничения режима text: этап 89
   недоступен (требует исполнения примеров), а слой 2 этапа 90 агент
   выполняет статически по приложенным исходникам — невоспроизводимое
   поведение честно получает `ЧАСТИЧНО`, как и предписывает промпт.

Не рекомендуем обходить подтверждения обёртками-автокликерами (expect/yes):
это ломается на каждом обновлении CLI и обнуляет смысл контроля, ради
которого подтверждения включены. Режимы stdout/text решают ту же задачу,
сужая полномочия агента, а не обходя контроль.

### Примеры под конкретные инструменты (только примеры)

Qwen Code CLI (`--approval-mode yolo` обязателен — иначе CLI повиснет на
подтверждении записи файлов; авторизация выполняется до прогона):

```yaml
agent:
  command: "qwen --approval-mode yolo -m {model} -p {prompt_text}"
models:
  "0": qwen3-coder-flash
  "7": qwen3-coder-plus
```

Kimi CLI (промпт текстом, режим без интерактива):

```yaml
agent:
  command: "kimi --print --afk -p {prompt_text}"
```

Любой другой корпоративный CLI подключается так же: соберите команду из
плейсхолдеров выше и проверьте контракт одним этапом
(`python runner.py --stages 0`).

## Маршрутизация моделей по этапам

Таблица уровней (восстановлена из MODEL_TIERS v1; конкретные модели задаёт
ваш CLI, runner подставляет уровень в `{model}` команды агента):

| Этапы | Уровень | Почему |
|---|---|---|
| 0, 1, 2, 3, 4, 89 | дешёвый (extraction) | извлечение по жёстким схемам; ошибки ловит детерминированный слой |
| 5, 6, 7, 8 | старший (synthesis) | синтез потоков, формулировки, сборка SRS |
| 90 | старший, **другой вендор** | независимый аудит |
| 92 | старший, **другой вендор** | инверсная верификация |

**Правило кросс-вендорной валидации: этапы 90 и 92 гоняет НЕ та модель, что
этап 4.** Валидация тем же семейством моделей склонна подтверждать собственные
формулировки. Задаётся в `config.yaml: agent.by_stage["90"|"92"]`; runner
останавливает прогон, если команда этапа 90/92 совпадает с командой этапа 4.

## Критерий приёмки

Прогон принят, если этап 90 даёт **не ниже 97% вердиктов ПОДТВЕРЖДЕНО**
(порог — `config.yaml: thresholds.stage90_confirmed_pct`). Ниже порога — не
«доработать формулировки», а вернуться на этап 4 и исправить правила по коду:
причина почти всегда в них. Сводка прогона показывает и точность (этап 90),
и полноту (`reports/coverage.md`: доля веток `raise`/`if`/`match`, покрытых
правилами, и функции без единого правила).

Во втором прогоне независимая сверка показала: 571 ссылка `файл:строка` — все
корректны, 145 цитат — 144 дословны. Единственное расхождение (сокращённая
цитата docstring) поймали одновременно и внешняя проверка, и слой 1 этапа 90.

Уроки этих прогонов в v3 разложены по слоям:

* **осталось в промптах (смысл):** тесты — не точки входа; `enclosing`
  обязателен и определяется по телу функции; не спасать требование
  доброжелательной интерпретацией; сверка по характерному фрагменту сообщения,
  а не по общему слову; при провале сначала показать, чем проверялось;
* **ушло в код (механика):** дословность цитат и привязка `source`
  (`checks/evidence_binding.py`), диапазоны идентификаторов
  (`checks/id_allocator.py`), полнота счётом и фиксированные колонки
  трассировки (`checks/completeness.py`), маскирование секретов
  (`checks/secrets_mask.py`), покрытие ветвлений (`checks/coverage.py`),
  имена файлов артефактов и подстановка переменных (`runner.py`).
