# Промпт: Этап 10 — Инкрементальная синхронизация базы знаний (для CLI-агента)

> **Пути в этом промпте относительные** (`workspace/...`). Он перенесён из
> исходного комплекта без изменений, потому что уже написан под CLI-агента.
> Перед запуском выполните агента с рабочим каталогом, в котором лежит
> `workspace/`, либо замените `workspace/` на `{WS}` тем же `sed`, что и в
> остальных этапах — см. `RUNBOOK.md`.

## Роль
Ты — системный аналитик, поддерживающий актуальность specs library
(`openspec/specs/`) и артефактов пайплайна при изменениях кода.
Полный реверс не выполняется: только точечные правки по фактическому дифу.

## Назначение и границы
Этап ловит изменения, прошедшие МИМО spec-процесса (хотфиксы, правки других
команд, работа в legacy-ветках). Изменения, проведённые через
`openspec/changes` → `archive`, в specs уже учтены — этап это распознаёт
и не дублирует. Итог всегда оформляется как отдельная ветка/MR: дрейф
спецификаций проходит ревью человеком так же, как дрейф кода.

## Предусловия
- `workspace/final/baseline.lock` существует:
  ```yaml
  repos:
    - name: <repo>
      ref: <commit срез а, от которого строилась база>
  last_sync: <дата>
  ```
  (Создаётся этапом 09; если нет — заполни вручную коммитами среза и остановись
  для подтверждения.)
- `traceability.csv` содержит file:lines и `openspec_path` для каждого правила.

## Порог применимости
Перед стартом оцени масштаб: если диф затрагивает > ~30% файлов, покрытых
трассировкой, или > половины capabilities — останови этап и рекомендуй
полный перепрогон пайплайна (этапы 1–9). Инкремент на таком объёме
дороже и хуже полного прохода.

## Режим выполнения

### Проход 0 — карта импакта (скрипт, БЕЗ LLM)
`git diff --name-status <baseline.ref>..HEAD` × traceability.csv →
`workspace/sync/impact_map.yaml`:
- `suspect_rules`: правила, чьи evidence-файлы изменены/удалены
  (+ их openspec_path)
- `uncovered_changes`: изменённые/новые файлы без единого правила
  (кандидаты на новое поведение)
- `deleted_files`: удалённые файлы и их правила
- `affected_capabilities`: сводка
- `touched_domain_api`: изменения в моделях/контрактах (по путям/маскам)
Детерминированный шаг: результат воспроизводим, LLM не участвует.

### Проход A — триаж дифа (фан-аут по модулям; дешёвая модель)
Одна задача = один затронутый модуль. Вход: его diff-ханки + его
suspect_rules (statement + evidence, без остального контекста).
Классифицируй каждый ханк:
- `cosmetic` — рефакторинг/переименование/перенос без смены поведения
  → действие: обновить только file:lines в трассировке
- `behavioral` — логика изменилась → правило на переизвлечение
- `structural` — сущности/статусы/контракты → правка design.md
- `already_specced` — поведение уже отражено в текущем spec.md
  (сверь формулировку; типично для изменений через openspec/changes)
Выход: `workspace/sync/triage/<module>.yaml`. Сомневаешься между
cosmetic и behavioral — выбирай behavioral (дороже, но безопасно).

### Проход B — переизвлечение (фан-аут; дешёвая модель, промпт этапа 4)
Только для модулей с behavioral/structural ханками и для uncovered_changes.
Тот же формат rules.yaml, тот же принцип «только наблюдаемое, с evidence».
Выход: `workspace/sync/re-extracts/<module>.rules.yaml`.

### Проход C — сверка и патч (по capability; средняя модель)
Вход: старые правила capability, переизвлечённые правила, её spec.md
и design.md, триаж-вердикты. Для каждого суспект-правила вердикт:
- `unchanged` — поведение то же → обновить только file:lines в trace
- `modified` — правь формулировку Requirement/Scenario ТОЧЕЧНО;
  ID и заголовок Requirement сохраняй, если суть та же (история и ссылки
  не должны ломаться); confidence пересчитай по новому evidence
- `added` — новое правило: под существующий FR (в trace) или новым
  Requirement с пометкой `<!-- нет FR: из инкремента <дата> -->`
- `removed` — evidence исчез без замены → удалить Requirement из spec.md
  (принцип as-is: код главнее), но обязательно зафиксировать в drift-отчёте
  с формулировкой удалённого поведения — ревьюер решит, потеря это или замысел
Также: патчи design.md при structural; если правка закрывает пункт из
`_open-questions.md` или подтверждает намерение из `unimplemented_intent.md` —
обнови и их (отметь «реализовано, см. <capability>»).
Правила патча: минимальный диф, не переписывать нетронутые блоки, не
переупорядочивать файл.

### Проход D — сборка (малый контекст)
- Обновить traceability.csv (file:lines, новые правила, удалённые — пометить).
- Обновить baseline.lock (новый ref, дата).
- Сгенерировать `workspace/sync/DRIFT_REPORT.md` для ревьюера:
  что изменилось в поведении системы (по вердиктам modified/added/removed),
  какие открытые вопросы закрылись, что удалено и требует взгляда человека,
  статистика (правил проверено/подтверждено/исправлено).
- `openspec validate`; создать ветку `sync/specs-<дата>`, закоммитить
  правки specs + отчёт, предложить MR. В main напрямую не писать.

## Самопроверка перед завершением
- Каждое suspect-правило получило вердикт; потерянных нет.
- Каждый uncovered_change либо дал новые правила, либо явно помечен
  «поведения не добавляет» (тесты, конфиги сборки, доки).
- Ни один Requirement не переименован/пересоздан без вердикта modified
  с изменением сути.
- Все removed отражены в DRIFT_REPORT.md.
- `openspec validate` без ошибок; diff по specs минимален (только
  затронутые блоки).
