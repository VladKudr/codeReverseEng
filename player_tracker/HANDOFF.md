# HANDOFF — контекст проекта player_tracker для продолжения работы

Документ для новой сессии (локальной или облачной): что просил пользователь,
что построено, какие решения приняты и почему, что проверено, что дальше.
Читать вместе с `player_tracker/README.md` (пользовательская документация)
и кодом; здесь — то, чего в README нет: история, обоснования, цифры, хвосты.

## 1. Задача пользователя (дословно и по смыслу)

> Мне требуется реализовать видео захват игрока на поле. Причём он может
> исчезать из фокуса и потом снова забегать, и его нужно снова ловить. Все
> игроки в футбол могут быть в одинаковой форме, это осложняет задачу.
> Съёмка осуществляться будет на iPhone 15 Pro Max.

Затем последовательно добавлены требования:

1. «В последствии я хотел бы собирать метрики исходя из детекции и
   фиксировать ошибки» → слой метрик и журнал ошибок, оценка по разметке.
2. «Мне нужно чтобы всё это работало через веб-приложение» → FastAPI +
   фронтенд без сборки.
3. «Запусти сейчас у меня локально на маке» → из облака нельзя; отправлена
   карточка задачи для локальной сессии + команды запуска (см. §7).

Пользователь пишет по-русски; код, докстринги, комментарии, README и
сообщения коммитов — по-русски (так принято во всём репозитории
`codeReverseEng`, чей основной проект — `req-reverse`, реверс требований из
кода; к трекеру он отношения не имеет, `player_tracker/` — отдельный
подпроект).

## 3. Архитектура и ключевые решения

### Три слоя по горизонту времени
* **Детектор** (`detection.py`): YOLOv8/11 через `ultralytics`, импорт
  ленивый — ядро и тесты работают без torch. `ScriptedDetector` для тестов.
  `conf=0.1` намеренно низкий: ByteTrack использует слабые детекции на
  втором проходе.
* **Мультитрекер** (`multitracker.py`): ByteTrack-подобный. Калман по
  (cx, cy, a, h), два прохода ассоциации (сильные/слабые детекции),
  стоимость `(1-w)·(1-IoU) + w·(1-cos)` с `appearance_weight=0.3`, строб
  Махаланобиса (для потерянных треков — только по позиции и с расширением
  `×(1+0.5·time_since_update)`). Держит id на секундах, не больше.
* **Слежение за целью** (`target.py`): долгоживущая модель одного игрока
  поверх мультитрекера. **Главный принцип: идентификатору мультитрекера не
  доверяем** — каждый кадр верифицируем, после потери ищем заново.

### Автомат состояний цели
`IDLE → ACTIVE ⇄ CONTESTED → LOST → ACTIVE`.
* `CONTESTED` — рамка цели пересекается с другим треком (IoU > 0.25):
  модель заморожена (галерея, номер, команда не обновляются), счётчик
  подозрений **сбрасывается** (дескриптор при перекрытии заведомо грязный —
  это был баг, найденный тестом `test_id_swap_during_contest_is_detected`),
  заморозка держится ещё `post_contest_freeze=5` кадров после.
* Отказы от трека (события): `released_swap` (6 кадров подряд калиброванное
  сходство < 0.30 вне перекрытия), `released_number` (на треке стабильно
  чужой номер, строгий порог веса 2.5), `released_team`. После отказа трек
  в cooldown 20 кадров.
* Потеря (`lost`): мультитрекер не выдал детекцию для трека цели.

### Признаки при повторном захвате (`TargetFollower._score`)
| Признак | Роль | Вес |
|---|---|---|
| `app` внешность | всегда; сходство с галереей = 0.6·max + 0.4·centroid, **калибруется**: `lo = mean(чужие) + 0.5·std`, `hi = mean(свои)` по EMA (`momentum 0.98`, минимум 30 образцов), до калибровки 0.60…0.95 | 1.0 |
| `number` | совпал → 1.0; противоречит → жёсткий отказ | 1.5 |
| `team` | другая команда → жёсткий отказ (метка трека — большинство из ≥5 голосов) | — |
| `motion` | гаусс от расстояния до экстраполяции (σ = 0.8 + 0.12·dt высот рамки), экстраполяция не дальше 8 кадров; вес ×exp(−dt/45), ×0.5 если цель ушла через край | 0.8 |
| `size` | log-отношение высот, σ=0.35; вес ×exp(−dt/150) | 0.3 |
| `cont` | тот же id мультитрекера после краткого пропуска; вес ×exp(−dt/12) | 0.7 |

Решение о захвате — три предохранителя одновременно: балл ≥ `accept_thr=0.55`,
отрыв от второго ≥ `margin=0.12` **и отдельно отрыв по признакам личности
(app/number/cont) ≥ `margin_identity=0.08`** (иначе после долгой потери спор
двойников решало бы движение — найдено тестом
`test_ambiguous_when_two_lookalikes_and_no_number`), подтверждение
`confirm_frames=3` кадра подряд (1 кадр для «непрерывного» кандидата при
потере ≤ 12 кадров). Иначе `LOST` + `ambiguous=True` + список кандидатов —
для ручного выбора (`Pipeline.reselect(track_id)`). Ложный захват
одноклубника считается хуже честного «потерян».

### Внешность при одинаковой форме
`PartColorEncoder`: HSV-гистограммы по 5 горизонтальным полосам с весами
head 1.0, torso 0.35, shorts 0.30, legs 0.80, boots 0.60; тон/насыщенность
и яркость нормируются порознь, яркость с весом 0.5 (иначе у одноклубников
сходство ~0.9 и опонент неотличим — найдено тестом). Центральные 60 % ширины
рамки (края — трава и соседи). Опционально OSNet через `torchreid`
(`--encoder osnet`, композиция с цветом 1.0/0.6). Все векторы L2, сходство
косинусное.

Галерея: до 40 образцов, добавление не чаще раза в 5 кадров при новизне
(max-сходство < 0.98), при переполнении вытесняется самый избыточный;
только в `ACTIVE`, не у края кадра, при калиброванном сходстве ≥ 0.35.

### Номер и команда
* `jersey.NumberVotes`: голоса с весом = уверенность OCR; вердикт при весе
  ≥ 1.2 и перевесе над вторым ≥ 2×. Для **отказа** от трека порог строже
  (2.5), чтобы пара ошибочных прочтений не сбрасывала цель. Голоса трека не
  стираются при поглощении в модель (был баг). OCR — `easyocr` опционально;
  политика вызова в `pipeline._read_numbers`: цель раз в 5 кадров в ACTIVE,
  до 6 кандидатов раз в 2 кадра в LOST.
* `team.TeamClassifier`: медианный Lab-цвет торса, k-means на 2 кластера
  (свой, без sklearn) после 60 образцов; «прочие» (судья, вратарь) — дальше
  `max(2.5·median_spread, 18)` от обоих центров. Используется только как
  фильтр «не та команда».

### Видео iPhone (`video.py`)
Чтение через ffmpeg из `imageio-ffmpeg` (ставится pip, есть libx264 и
zscale): HEVC, тонмаппинг HDR (HLG `arib-std-b67`/PQ → BT.709, `tonemap=hable`;
при ошибке фильтра — откат без тонмаппинга с предупреждением), автоповорот,
`-fps_mode cfr`, масштаб (`--width 1280` по умолчанию), фрагмент. Метаданные:
ffprobe → разбор `ffmpeg -i` (в imageio-ffmpeg нет ffprobe) → OpenCV.
`FrameWriter` пишет H.264 (libx264, yuv420p, faststart) — mp4v из OpenCV
браузеры не играют. Откат на OpenCV везде с предупреждением.

### Метрики и ошибки (`metrics.py`)
`RunMetrics.observe` на каждом кадре → `summary()`: detection / tracks /
target / ocr / speed / errors. `ErrorLog`: виды и серьёзность в `ERROR_KINDS`,
серии однотипных кадровых замечаний схлопываются (`run_length`,
`last_frame`), вывод JSONL + Markdown, сортировка по кадру. Исключения
компонентов перехватываются в `Pipeline._guard` (кадр как пустой,
`tolerate_errors=True`; `--strict` — наружу). `Pipeline.finalize()` — цель
не найдена до конца ролика → `init_failed`. Оценка по разметке
`evaluate(records, truth, log)`: TP / wrong_target / missed_target /
true_absent / false_track, recall, precision, IoU, id_switches, MOTA для
одной цели; разметка JSON `{"frames": {"12": [x1,y1,x2,y2], "13": null}}`
или CSV `frame,x1,y1,x2,y2` в координатах исходного кадра.

### Веб (`webapp/`)
FastAPI (`server.py`) + `jobs.py` (задачи в потоках, `data/videos`,
`data/jobs/<id>/state.json`, переживает перезапуск — незавершённые
помечаются failed) + `static/` (vanilla JS). Фабрики
детектора/кодировщика/OCR в `JobManager` подменяются в тестах. Аутентификации
нет — сознательно, локальный инструмент. Клик по кадру → пиксели
уменьшенного кадра / `X-Scale` → координаты исходного кадра.

## 4. Что проверено

* **115 тестов** в репозитории (62 старых `tests/` + 53 в
  `player_tracker/tests/`), нейросети не нужны: сценарные детекции,
  синтетические векторы, рисованные «игроки» (`tests/_synth.py`;
  помощники вынесены из conftest, потому что установленный пакет `tests`
  в site-packages затенял `tests.conftest`).
* Живой прогон с YOLOv8n на CPU: ролик-панорама по фото `bus.jpg`
  (человек уходит за левый край и возвращается): `locked` кадр 2, `lost`
  48, `reacquired` 112 тем же человеком; по разметке precision 1.0, recall
  0.757, IoU 0.83, все пропуски — цель видна частично у края. ~15–18 кадр/с
  при 540×360, imgsz 640, 4 ядра CPU.
* Веб-приложение прогнано в Chromium через Playwright: загрузка → клик →
  задача до конца → оценка по разметке; числа совпали с CLI, ошибок в
  консоли нет (кроме favicon, теперь 204).
* **Не проверено на реальном футбольном ролике** — внешние медиахосты в
  облачной среде были закрыты. Это первый следующий шаг.

## 5. Известные ограничения и хвосты

* Пороги `TargetConfig` подобраны на синтетике и одном полу-реальном ролике.
  На реальном матче первым делом смотреть калибровку (`model.bounds()`),
  долю `ambiguous`, ложные `released_swap`.
* Цветовой дескриптор чувствителен к освещению; OSNet (`torchreid`)
  не тестировался в среде (нет весов), код `TorchReidEncoder` написан по
  API torchreid, `pragma: no cover`.
* OCR `EasyOcrReader` — то же: код по API easyocr, не прогонялся.
* Тонмаппинг HDR проверялся только на уровне сборки фильтра (`zscale`
  присутствует в бинарнике), не на настоящем Dolby Vision-ролике.
* Веб: задачи в потоках одного процесса, без очереди и без аутентификации;
  видео грузится целиком (нет chunked upload); нет UI для `reselect`
  (ручной выбор кандидата при `ambiguous`) — есть только метод в `Pipeline`.
* `ScriptedNumberReader` обрабатывается в pipeline через `isinstance` —
  тестовый хак, при желании заменить на протокол `read_for`.
* Root-тесты `tests/` требуют `pyyaml`, `jsonschema` (не в
  `player_tracker/requirements.txt`).

## 7. Запуск локально (Mac)

```sh
git fetch origin claude/video-capture-player-tracking-bofmel
git checkout claude/video-capture-player-tracking-bofmel
cd player_tracker
python3 -m venv .venv && source .venv/bin/activate      # Python ≥ 3.10
```

`player_tracker/weights/`. Данные веба —

## 9. Сессия 2026-09-15: первый реальный ролик (локально, Mac)

Пользователь загрузил ролик (Telegram-пересжатие, 848×464, 30 fps, 372 кадра:
тренировка детей, съёмка из-за забора с сеткой и перилами, панорамирование с
рук) и попросил: «он потерял игрока почти сразу — протестируй сам, улучши,
добейся точности позиционирования 99.7 %». **99.7 % не достигнуто**:
текущий результат 92–95 % (см. таблицу в README, «Проверка на реальном
ролике»). Ниже — что выяснилось и почему так.

### Что было не так
* Веб по умолчанию считал YOLO на CPU (ultralytics на Mac без `device="mps"`
  не использует GPU) — 5 кадр/с; теперь авто cuda → mps → cpu, 11 кадр/с.
* Одна из двух задач пользователя стартовала с точкой (0, 0): клик до загрузки
  кадра (`naturalWidth = 0`) — исправлено во фронтенде.
* Захват в кадре выбора ждал подтверждения трека (3 сильные детекции), а цель
  стояла вплотную к соседу: клик ранжировался по «меньшей рамке» и попадал на
  край соседа. Теперь — по удалённости точки от центра рамки
  (`geometry.click_rank`) и сразу, даже по слабой детекции (`MultiTracker.spawn`).
* Цветовой дескриптор с малым весом торса не отличал розовую манишку от
  красной формы — ложный захват №10; калибровка «свои/чужие» не спасала.
* Команды по цвету при 4 цветах манишек давали ложные «чужая команда»;
  голоса команды трека копились за всю жизнь id, включая прежнего владельца.

### Разметка (главный урок)
Разметить цель пришлось самому, по увеличенным кадрам с номерами детекций и
по координатам сцены (компенсация камеры). Первая версия разметки была
неверной: решил, что со 139-го кадра цель навсегда скрыта в очереди, а на
280–358 она проходит упражнение второй раз — в этом ракурсе манишка почти
белая. Нашёл это, когда трекер «ложно» захватил игрока с контрастом +0.29.
Итоговая разметка: 179 кадров видна, 45 partial, 148 hidden; формат —
см. README («Оценка по разметке»). Разметка: `~/Downloads/video_2026-09-15_16-21-12.truth.json`
и `player_tracker/data/truth/` (в .gitignore), в репозиторий не добавлена — ролик личный.

### Что сделано (по убыванию эффекта)
1. `camera.py` — компенсация движения камеры (LK по фону с маской людей,
   RANSAC partial affine) в мультитрекере и модели цели.
2. Контраст внешности: сходство с галереей минус сходство с банком «соседей»
   (дескрипторы игроков, видимых одновременно с целью); решения — по среднему
   за последние *чистые* кадры трека (`TargetFollower.evidence`), а не по кадру.
3. «Соседство» (`coexist`): трек, долго видимый одновременно с целью без
   перекрытия, не может быть целью. Сбрасывается при разрыве трека > 8 кадров
   и при `released_swap` (набрано на подменённом треке).
4. «Досягаемость» (`reach_*`): после потери посреди кадра кандидат дальше
   `2 + 0.015·dt` высот не захватывается, но участвует в проверке двойников;
   номер снимает ограничение. Нужен против двойника в другой группе на поле.
5. Старт модели: пока банк соседей не набран, учимся на кадре, только если
   трек цели похож на галерею сильнее любого другого видимого игрока
   (`bootstrap_margin`) — без этого 2 из 6 детекторов проваливались до 58 %.
6. Относительный захват (`app_floor`, `app_rel_margin`): внешность средняя, но
   все остальные кандидаты заметно хуже — берём (слабые детекторы).
7. Переход на соседний трек в перекрытии (`_check_switch`, событие `switched`),
   подмена по «грязным» кадрам в затяжном перекрытии (`swap_contrast_dirty`).
8. `offline.refine_online` — уточнение после прогона (backfill, обрезка
   подмены, интерполяция разрывов) + пересчёт метрик по итоговым решениям
   (`Pipeline.final_observations`), видео пишется вторым проходом.
9. `ThumbnailEncoder` + `default_color_encoder()`.
10. Оценка: `partial`/`hidden`, `accuracy`.

### Что пробовал и отверг (с цифрами)
* DINOv2-small/base (HF transformers) как дескриптор: AUC цель/остальные
  0.81–0.85 против 0.99 у цвет+миниатюра. Пакет удалён.

## 11. Сессия 2026-09-16: мяч и тактическая доска

Запрос: «разбор даёт чёткое понимание, что не распознан мяч — без него делать
выводы по игре невозможно: улучшить распознавание мяча до уровня детекции
игроков; дальше — визуализация на тактической доске перемещений всех игроков,
в том числе того, что в фокусе».

### Что померено до работы (`IMG_7463.MOV`, 1280×720, мяч 4–8 px)
На 249 кадрах (каждый 10-й) доля кадров, где есть хоть один кандидат мяча:

| вариант | conf ≥ 0.25 | conf ≥ 0.05 | время |
|---|---|---|---|
| yolo11s @1280 (как было) | 0.16 | 0.34 | 76 мс |
| yolo11s @1920 | 0.22 | 0.70 | 149 мс |
| yolo11x @1280 | 0.23 | 0.51 | 465 мс |
| **yolo11s, плитки 640→1280 (×2)** | **0.31** | **0.92** | 374 мс (250 мс батчем) |
| yolo11s, плитки 427→1280 (×3) | — | 0.51 | 905 мс |

Вывод: даёт увеличение масштаба, а не более тяжёлая модель; ×3 хуже ×2
(мяч выходит за «привычный» сетке размер, растёт фон).

### Как отделяется игровой мяч (это была основная работа)
Кандидатов много и почти все — настоящие мячи: у забора лежат 5–8 запасных.
Плюс головы зрителей у края кадра, оранжевые бутсы, конусы, бутылки у камеры.
Работают (в порядке вклада):
1. схема поля — мяч вне поля с запасом 3 м + 8 % глубины отбрасывается;
2. неподвижность в координатах сцены: кандидат, рядом с которым мяч есть и за
   ~1 с до, и через ~1 с после, в окне ±4 с — запасной (1600 из 5300 кандидатов);
3. размер против ожидаемого диаметра в этой точке земли (`ground.py`) —
   головы/бутылки/фонари; мяч в верхних 60 % рамки человека — голова/руки;
4. слабая детекция (< 0.2) вдали от игроков не может начать цепочку;
   цепочка должна набрать ≥ 0.5 «ценности» сама по себе.

Ручная проверка выборок (64 найденных позиции с крупными вырезками): точность
выросла с ~72 % до ~87 %; в оценках разрывов — около половины (поэтому они
показываются отдельно и в метриках названы оценкой).

### Доска
`board.py` строит `board.json` (10 кадров/с): позиции всех треков в метрах поля
(глубина — по плоскости поля, а не по росту своей рамки: у закрытых игроков
рамка ниже), команда трека по кластеру цвета формы, цель, мяч. Журнал треков
прогона сохраняется в `tracks.npz` (`offline.TrackLog` + номер детекции для
цвета торса). Фронтенд рисует доску рядом с видео (следы, номера треков,
подсветка цели), `game_context` добавляет владение/дистанцию до мяча/линию
обороны в ленту метрик и в ИИ-разбор (инструмент `get_positions`).

### Хвосты
* мяч в борьбе у ног не виден физически — помогло бы 4K или съёмка сбоку;
* оценка владения «по ближайшему игроку до 2 м» груба, 56 % времени «ничей»;
* команда трека по цвету формы ошибается на вратаре и тренерах в тёмном
  (они попадают в «прочие» или в тёмную команду);
* глубина по плоскости поля предполагает ровную землю и одинаковый рост:
  взрослые у бровки «приближаются», дети в глубине — наоборот;
* `inputs.npz` старых задач не содержит мяча с плиток — при первом построении
  доски делается отдельный проход по `frames.mp4` (стадия `ball`).

### Дополнение: «вне игры» (запрос пользователя сразу после доски)
«Есть игроки, которые стоят на бровке, не участвуют в игре — пометить и исключить из анализа, чтобы и
на доске не появлялись». Сделано `board.classify_roles`: по следу трека на поле — доля времени за
линиями (> 1 м), разброс положения на секунду жизни (стоит/двигается) и медиана расстояния до «места
игры» (медиана положений всех треков кадра). Пороги: за полем ≥ 50 % времени; или разброс < 0.25 м/с
при ≥ 30 % времени у боковой линии; или ≥ 35 % у линии + ≥ 16 м до игры при разбросе < 0.8 м/с.
Лицевые линии намеренно не считаются «бровкой» (иначе вратарь на линии ворот попадает под правило),
треки короче 4 с не классифицируются, трек цели защищён. Ручные пометки (`JobState.track_roles`,
`POST /api/jobs/{id}/board/tracks`) сильнее автоматики и пересчитывают доску и метрики без перепрогона;
исключённые люди не участвуют в «ближайшем игроке» и единоборствах (`player_metrics(ignore_boxes=...)`).
Проверено на `IMG_7463.MOV`: 13 треков исключено, все шесть проверенных вручную — действительно зрители
у камеры, дети у дальней бровки и тренеры; на кадре осталось 14.7 человек вместо 17.7.
Заодно: статика фронтенда отдаётся с `Cache-Control: no-store`, а в `index.html` к app.js/style.css
добавляется версия по mtime — иначе браузер держал старый app.js после обновления.

## 15. Состав: пометка относится к человеку, а не к треку (17.09.2026, старшая модель)

**Ошибка от пользователя:** выключенный вручную человек через несколько кадров возвращался на доску.
**Причина (замер, игра 7×7, 83 с):** 385 треков на ~19 человек в кадре — человек рвётся на ~7 фрагментов, у 92 % новых
треков рядом только что оборвавшийся. Пометка стояла на одном фрагменте.

**Решение — `tracker/roster.py`:**
1. `link_tracks` — фрагменты → люди: продолжение (≤ 3 с, встречный прогноз положения в координатах сцены `camreg`, рост,
   цвет формы, только взаимно лучшая пара), стоящие на одном месте (любой разрыв), запрет «двое одновременно».
2. `Mark` — событие на линии времени человека: целиком или с кадра `at` (замена: «ушёл с поля / вышел на поле»).
3. `resolve` — кто вне игры по кадрам и почему (`manual` / `person` / `similar` / `default`). `similar`: человек без пометок
   сравнивается по внешности (признаки трекера из `inputs.npz`, косинус) с примерами. Примеры: помеченные люди + остальные
   люди на КАДРЕ, где оператор ставил пометки (они — примеры роли по умолчанию; поэтому в интерфейсе совет «отметьте на
   одном кадре всех»).
4. Режим состава `JobState.roster_mode`: `all` — в игре все, кроме выключенных; `marked` — в игре только отмеченные и похожие.
5. Доска: `tracks[id].off` — отрезки кадров вне игры, `why`, `person`; `role == "sideline"`, если вне игры ≥ 90 % трека
   (совместимость). `board.track_off(meta, frame)` — в игровом контексте, метриках («ближайший игрок»), разборе ИИ.
   Цель слежения выключается только явной пометкой.
6. API: `POST /board/tracks {track_id, role, frame, scope: all|from, defer}`; `POST /board/roster/apply|clear|mode`.
   Фронтенд: щелчок виден сразу (`pendingMarks`), пересчёт (5–6 с) — один раз через 1.8 с после последнего щелчка.

**Стенд (`tools/roster_check/`, эталон «кто играет» размечен глазами на кадрах 300/1200/2100 ролика 1032, в `common.py`):**

| Пометки на одном кадре → проверка на двух других | игроки на доске | лишние убраны |
|---|---|---|
| по треку, как было («выключаю лишних») | 20/20 | 3/14 |
| по человеку (одна склейка) | 20/20 | 4/14 |
| человек + похожие, «выключаю лишних» (5–8 щелчков) | 18–21 из 20–23 | 9/14, 12/13, 9/11 |
| человек + похожие, «отмечаю игроков» (9–12 щелчков) | 17–18 из 20–23 | 7/14, 11/13, 9/11 |
| пометки на двух кадрах → третий, «выключаю лишних» | 9/9 | 7/8 |

Вывод: одной склейки мало (камера уводит людей из кадра дольше чем на 3 с); решает сходство по внешности; второй кадр
разметки заметно улучшает. «Выключаю лишних» надёжнее для игроков и дешевле по щелчкам — оставлен по умолчанию.

**Хвосты:** (1) рост рамки относительно ожидаемого (взрослый/ребёнок) сходству не помог — не используется;
(2) тёмная форма соперника похожа на тёмную одежду взрослых — главный источник ошибок `similar`; помогла бы позиция
относительно отмеченного поля; (3) эталон мал (3 кадра, 1 ролик) — расширить; (4) `test_two_stage_run…` дважды из ~25
прогонов падал в общем прогоне (поодиночке не воспроизводится) — вероятно, гонка по времени с фоновой привязкой кадров;
