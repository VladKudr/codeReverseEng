# player_tracker — слежение за одним игроком на видео с iPhone 15 Pro Max

Задача: на ролике футбольного матча удерживать рамку на **одном выбранном
игроке**. Игрок уходит из кадра (или за другого игрока) и возвращается — его
надо поймать снова; все игроки одной команды одеты одинаково.

## Как это решается

Три слоя, каждый отвечает за свой горизонт времени:

| Слой | Горизонт | Что делает | Модуль |
|---|---|---|---|
| Детектор | кадр | рамки людей (YOLO11, класс `person`) | `tracker/detection.py` |
| Камера | кадр | движение кадра при съёмке с рук (оптический поток по фону, RANSAC) — переносит предсказания треков и последнюю позицию цели | `tracker/camera.py` |
| Мультитрекер | секунды | ByteTrack-подобная ассоциация: Калман + IoU + внешность, слабые детекции на втором проходе — держит id при коротких пропусках | `tracker/multitracker.py` |
| Слежение за целью | весь ролик | долгоживущая модель **одного** игрока: галерея внешности и банк «соседей», номер, команда, движение; верификация трека и повторный захват | `tracker/target.py` |
| Уточнение | весь ролик | после прогона, взглядом вперёд: убирает задержку захвата, поздно замеченные подмены id, короткие разрывы | `tracker/offline.py` |

Ключевая идея — **не доверять идентификатору мультитрекера**. Он живёт до
первого столкновения двух игроков в одинаковой форме. Поверх него
`TargetFollower` каждый кадр проверяет, что трек всё ещё похож на цель, а
после потери ищет её среди всех видимых треков по нескольким независимым
признакам:

| Признак | Роль | Почему |
|---|---|---|
| `app` — внешность | всегда, основной | **контраст**: сходство с галереей цели минус сходство с банком «соседей» — игроков, видимых одновременно с целью; усредняется по последним чистым (без перекрытия) кадрам трека. Одинаковая форма поднимает оба сходства, разность остаётся информативной |
| соседство | жёсткий отказ | трек, долго видимый одновременно с целью без перекрытия, — не цель, как бы ни был похож |
| досягаемость | жёсткий отказ | цель, скрывшаяся за игроками (не за краем кадра), не телепортируется: кандидат дальше `2 + 0.015·dt` высот фигуры от места потери (в координатах без движения камеры) не захватывается, но как двойник учитывается |
| `number` — номер | совпал → сильное «за»; противоречит → жёсткий отказ | единственный признак, который отличает одноклубников надёжно; читается редко, поэтому копятся голоса (`jersey.NumberVotes`) |
| `team` — цвет формы | другая команда → жёсткий отказ | двухкластерная модель Lab-цвета торса; судья/вратарь — «прочие» |
| `motion` — движение | вес затухает с временем потери | камера в руках и большое поле: через секунду позиция мало что значит |
| `size` — рост в пикселях | слабый | защищает от захвата игрока на другом плане |
| `cont` — непрерывность | бонус тому же id после краткого пропуска | ByteTrack и так гейтит по движению |

Захват происходит только при трёх условиях сразу: балл выше порога, **отрыв
от второго кандидата** (отдельно — по «идентификационным» признакам, чтобы
движение не решало спор двойников) и подтверждение на нескольких кадрах
подряд. Иначе состояние остаётся `LOST`, а в выходе лежит список кандидатов
с пометкой `ambiguous` — для ручного выбора. Ложный захват одноклубника
хуже честного «потерян».

Дескриптор внешности (`appearance.default_color_encoder`) — гистограммы по
полосам тела (`PartColorEncoder`: голова и гетры весят больше формы) плюс
миниатюра фигуры 8×24 в Lab без среднего цвета (`ThumbnailEncoder`):
гистограмма не знает, *где* цвет, а миниатюра видит рукава, шорты, волосы.
Проверено на реальном ролике: нейросетевые эмбеддинги общего назначения
(DINOv2) и линейный классификатор на кадр различают детей в одинаковых
манишках хуже (AUC 0.81–0.94 против 0.99). При наличии `torchreid`
подключается OSNet (`--encoder osnet`).

Цвет формы (`team`) используется, только если выборка действительно делится
на две формы: на тренировке с манишками трёх-четырёх цветов классификатор
молчит. Голоса за команду трека берутся по последним 15 кадрам — id
мультитрекера переходит к другому игроку, и голоса прежнего владельца не
должны решать за нового.

**Уточнение по всему ролику** (`offline.refine_online`, по умолчанию включено
в CLI и вебе; `--no-refine`). Личность решает онлайн-автомат; после прогона
по журналу мультитрекера (id, рамка, дескриптор каждой детекции, движение
камеры) исправляется то, что ему недоступно из-за причинности: кадры, где
цель уже была видна на захваченном позже треке, дописываются назад (пока трек
не перекрывался и похож на цель); кадры между началом перекрытия и
`released_swap` помечаются потерей; разрывы до 8 кадров интерполируются в
координатах сцены. Глобальное переназначение личности по всему ролику
пробовалось и отвергнуто: двойники из других групп выигрывают по внешности.

Состояния цели: `IDLE` → `ACTIVE` ⇄ `CONTESTED` (перекрыта другим игроком:
модель заморожена, подозрения не копятся) → `LOST` (поиск) → `ACTIVE`
(событие `reacquired`). Отказы от трека: `released_swap` (после перекрытия
трек стал непохож — подмена id), `released_number`, `released_team`.

## Запуск

```sh
pip install -r requirements.txt          # ядро + ultralytics
# цель — рамка на первом кадре (координаты исходного 4K-кадра), номер известен
python track.py IMG_1234.MOV --init-box 1810,620,1890,840 --number 10 --out out/
# цель — точка (клик), фрагмент с 12-й секунды, 900 кадров
python track.py IMG_1234.MOV --init-point 1850,730 --start-sec 12 --max-frames 900 --out out/
# интерактивно (нужен opencv-python с GUI): окно, клик по игроку, Enter
python track.py IMG_1234.MOV --select --out out/
```

Полезные флаги: `--width 1280` (ширина кадра обработки; 4K целиком
бессмысленно), `--weights yolo11s.pt` (по умолчанию; `yolo11n.pt` вдвое
быстрее, `yolo11x.pt` в ~7 раз медленнее — см. таблицу ниже), `--imgsz 1280`,
`--device` (по умолчанию cuda → mps → cpu: ultralytics сам на Mac считает на
CPU), `--encoder osnet`, `--ocr easyocr`, `--tonemap on|off`, `--no-team`,
`--no-refine`. Веса скачиваются в `player_tracker/weights/`.

Выход в `--out`:

* `track.json` — по кадрам: состояние, id, рамка (в координатах исходного
  кадра), уверенность, событие, кандидаты с баллами по признакам;
* `track.csv` — то же кратко; `events.log` — только события и неоднозначности;
* `summary.json` — доля отслеженных кадров, число потерь/захватов/отказов;
* `annotated.mp4` — визуализация: зелёная рамка — цель, жёлтая — перекрыта,
  красная надпись `LOST` и оранжевые кандидаты с баллами — поиск.

Ручное вмешательство: `Pipeline.reselect(track_id)` фиксирует цель на
указанном треке (например, по `ambiguous`-кандидатам из `events.log`).

## Метрики и журнал ошибок

Каждый прогон пишет в `--out` (`tracker/metrics.py`):

* `metrics.json` — сводка: детекция (людей на кадр, доля сильных детекций,
  кадры без детекций, распределение уверенности и высоты фигур в пикселях),
  треки (уникальных id, на кадр), цель (доля отслеженных кадров, перекрытия,
  пропуски детекций на треке, эпизоды потерь и их длина, повторные захваты,
  смены id, неоднозначные кадры), OCR (попытки/прочтения), скорость
  (мс на кадр, p90, кадр/с), счётчики ошибок по видам и серьёзности;
* `frame_stats.csv` — то же по кадрам, для графиков;
* `errors.jsonl` — журнал ошибок по одной записи в строке: кадр, время, вид,
  серьёзность, сообщение, подробности (id трека, кандидаты с баллами,
  traceback). Серии однотипных кадровых замечаний схлопываются в одну запись
  с длиной серии;
* `errors.md` — та же сводка для чтения глазами.

Виды ошибок: `exception` (сбой детектора/кодировщика/OCR — кадр обрабатывается
как пустой, прогон продолжается; `--strict` останавливает), `init_failed`,
`target_lost`, `released_swap|number|team`, `ambiguous`, `long_loss`,
`no_detections`, `detection_dropout`, `low_confidence`, `target_at_border`,
`ocr_miss`, и по разметке — `wrong_target`, `missed_target`.

**Оценка по разметке.** Файл `truth.json` в координатах исходного кадра:

```json
{"frames":  {"12": [x1, y1, x2, y2], "13": null},
 "partial": {"40": [x1, y1, x2, y2]},
 "hidden":  [139, 140, 141]}
```

`frames` — цель видна (`null` — цели в кадре нет); `partial` — цель частично
закрыта в группе игроков, рамка приблизительная: верно, если слежение честно
потеряно или рамка на цели с IoU ≥ 0.3; `hidden` — цель в кадре, но
полностью закрыта: верно только «потеряна». CSV: `frame,x1,y1,x2,y2[,state]`.
`--truth truth.json` даёт `evaluation.json`: **`accuracy`** — доля верных
кадров среди размеченных («точность позиционирования»), TP /
`wrong_target` / `missed_target` / `false_track`, `partial_ok|wrong`,
`hidden_ok|wrong`, recall, precision, средний IoU, переключения личности,
MOTA для одной цели. Ошибки
по разметке попадают в тот же журнал с кандидатами на момент пропуска —
из него видно, кого автомат рассматривал и почему не взял.

Программно: `pipe.metrics.summary()`, `pipe.errors.records`,
`metrics.evaluate(records, truth, pipe.errors)`.

## Веб-приложение

```sh
pip install -r requirements.txt
python serve.py --host 0.0.0.0 --port 8000 --data data/
```

Откройте `http://<хост>:8000/` (с iPhone — по адресу компьютера в той же
сети). Сценарий на одной странице:

1. **Ролик** — загрузка `.MOV`/`.mp4` прямо с телефона; показываются
   разрешение, fps, HDR/SDR, поворот, VFR. Тот же файл второй раз не
   загружается (сверка по SHA-256) — открывается прежний ролик; копии,
   загруженные раньше, сливаются при старте сервера (задачи переносятся на
   первую загрузку). При выборе ролика показано, что по нему уже сделано
   (игрок, опрос, поправки, разборы) с кнопкой «Открыть»; запуск слежения за
   уже отслеженным игроком (та же точка в тот же момент) предлагает открыть
   готовый результат.
2. **Выбор игрока** — кадр в нужный момент (слайдер), клик по игроку
   (точка переводится в координаты исходного кадра), номер, **опрос об игроке**
   (обязательно: возраст, позиция, формат игры 4×4 / 5×5 / 6×6 / 7×7 / 8×8 — полевые игроки плюс вратарь, 6×6 = 7 в команде; 11×11 — классика, 10 + вратарь; /
   11×11 / тренировка / иное; рост — по желанию), параметры
   (ширина обработки, веса YOLO, устройство, дескриптор, OCR, тонмаппинг,
   фрагмент). «Запустить слежение».
3. **Задачи** — список с прогрессом; задачи выполняются в фоне, состояние
   переживает перезапуск сервера (`data/jobs/<id>/state.json`).
4. **Результат** — размеченное видео (H.264, играет в браузере и на iPhone),
   цветная лента состояний по кадрам (клик — переход в видео), события,
   итог, метрики по группам, журнал ошибок (клик по строке — переход к
   кадру), загрузка разметки и оценка, ссылки на все файлы.
5. **Поправка цели** — пауза в нужном месте → «Исправить цель в этом кадре»:
   кадр с рамками найденных игроков (шаг ±1/±10 кадров, масштаб 1–3× с прокруткой к цели), клик по цели →
   «Цель здесь — перестроить дальше», или «Цели нет в кадре». Слежение
   перестраивается с учётом всех поправок по сохранённым данным кадров
   (детекции, дескрипторы, движение камеры — `inputs.npz`) без детектора:
   80-секундный ролик — десятки секунд вместо минут. Поправки копятся,
   удаляются крестиком. «Цель здесь» переводит слежение на указанного игрока
   и забывает выученное на прежнем (неверном) треке; «цели нет» — никто из
   видимых сейчас игроков не цель, пока их треки не прервутся. Решения
   автомата до кадра поправки не меняются; уточнение по ролику может сдвинуть
   соседние кадры (например, отменённый поправкой захват больше не
   продлевается назад).
6. **Метрики игрока** — время в кадре, дистанция и темп, средняя/максимальная
   скорость, зоны скорости (детские пороги), спринты, ускорения/торможения,
   единоборства (ближайший игрок < 1.5 м), «мяч рядом», тепловая карта по
   сцене, посекундный график (клик — переход в видео). Метры — **оценка** по
   росту игрока (поле «Рост») и углу обзора камеры: поперечное смещение
   ΔX = Δu·H/h от объектива не зависит, глубина — по изменению роста рамки
   (шумнее); панорамирование убрано компенсацией камеры. Точность ±20–30 %,
   точные метры требуют калибровки поля. Мяч — своя траектория по всему
   ролику (см. ниже), «мяч рядом» считается по ней; доля кадров, где мяч
   найден и где оценён, показывается рядом.
7. **Схема поля** (обязательна для разбора) — вид сверху: клик — где стоит
   камера (обычно за бровкой или за воротами), клик — что в центре первого
   кадра, клик — свои ворота; размер поля — из формата (правится). По ней
   положение игрока пересчитывается в метры поля (`tracker/pitch.py`:
   игрок = камера + X·вправо + Z·вдоль взгляда): трети (своя / средняя /
   чужая относительно атаки своей команды), фланги, метры к чужим и к своим
   воротам, направление каждого спринта, тепловая карта на схеме. Если игрок
   часто оказывается за полем — подсказка проверить отметки.
8. **ИИ-разбор** (DeepSeek) — опрос подставляется из задачи (правки
   сохраняются и пересчитывают метрики), плюс форма и «на что смотреть» →
   «Сделать разбор»; дальше чат с уточнениями.

   Как опрос влияет на расчёт (`tracker/profile.py`): **возраст** — пороги зон
   скорости (спринт от 4.0 м/с до 10 лет, 4.5 — 10–12, 5.0 — 13–15, 5.5 — 16+)
   и типичный рост по медианам ВОЗ, если рост не указан (рост — масштаб
   метров); **позиция** — по чему судить игрока (защитник: удержание позиции и
   страховка; нападающий: открывания, рывки, мяч в атаке; вратарь: беговые
   метрики второстепенны…); **формат** — ориентировочный размер поля и
   характер игры (4×4 ≈ 25–35 × 18–25 м, плотно, единоборства — норма;
   11×11 — длинные рывки, мяч рядом редко). Всё это передаётся модели как
   «Ориентиры», и в правилах сказано оценивать действия относительно роли и
   поля и отмечать, если фактическое положение не похоже на заявленную позицию. Модель не видит
   видео: получает выжимку метрик, качество данных, поправки и инструменты —
   посекундную ленту за отрезок, эпизоды (спринты, единоборства, мяч рядом),
   события слежения. Системные правила: только по данным, без выдуманных
   передач и ударов, оговорки про точность, отметки [мм:сс] (в вебе — переход
   по видео). В DeepSeek уходят только числа и текст. Ключ — переменная
   `DEEPSEEK_API_KEY` или `data/secrets.json` (`{"deepseek_api_key": "…"}`,
   каталог `data/` в git не попадает). Разборы сохраняются версиями: при
   открытии задачи показывается последний, повторный разбор по тем же данным
   не запрашивается (показывается сохранённый), «Новый разбор» добавляет
   версию, прежние доступны в списке (разборы до поправок помечены «по
   прежней версии слежения»).

API (`webapp/server.py`): `POST /api/videos`, `GET /api/videos/{id}/frame?t=`,
`POST /api/jobs`, `GET /api/jobs/{id}`, `POST /api/jobs/{id}/cancel`,
`GET /api/jobs/{id}/files/{name}`, `GET /api/jobs/{id}/frames`,
`POST /api/jobs/{id}/truth`; поправки — `GET /api/jobs/{id}/frame/{n}` (точный
кадр обработки из копии `frames.mp4`: у роликов iPhone номер кадра по времени
не находится), `GET /api/jobs/{id}/detections/{n}`,
`POST|DELETE /api/jobs/{id}/corrections`, `POST /api/jobs/{id}/rerun`;
`GET|POST /api/jobs/{id}/player-metrics`; опрос — поле `player` в `POST /api/jobs`,
`PUT /api/jobs/{id}/player`, варианты — `GET /api/profile/options`; `GET /api/ai/status`,
`GET|POST|DELETE /api/jobs/{id}/analysis` (версии: `new`, `session_id`), `GET /api/videos/{id}/jobs`. Документация — `/docs` (Swagger).

Аутентификации нет: приложение для локального запуска или доверенной сети.
Данные (ролики, задачи) лежат в `--data`; удаление — через интерфейс или API.

## Мяч и тактическая доска

Мяч в кадре 1280×720 с дальнего плана — 4–8 px, YOLO находит его на кадре
целиком лишь на ~16 % кадров. Поэтому:

* **Детекция на плитках** (`detection.YoloDetector.detect_balls`): кадр режется
  на перекрывающиеся плитки 640 px ниже неба и подаётся сетью со стороной 1280
  — мяч видно вдвое крупнее. На игровом ролике: мяч хотя бы одним кандидатом
  есть на 79 % кадров (было 34 %), цена — ~0.25 с/кадр сверх детекции людей.
  Плитки включены по умолчанию (`ball_tiles=False` — как раньше).
* **Плоскость поля** (`ground.py`): по рамкам всех людей кадра строится
  робастная прямая «рост человека от строки ног». Она даёт глубину любой точки
  земли (в том числе мяча, у которого своего роста нет) и ожидаемый диаметр
  мяча в этой точке — размерный фильтр отсекает головы зрителей, бутсы,
  бутылки, фонари.
* **Траектория игрового мяча** (`ball.py`): кандидаты связываются в треклеты в
  координатах сцены с гейтом по скорости в метрах; кандидаты, лежащие на одном
  месте секундами, — запасные мячи у забора; за пределами поля (если схема
  отмечена) мяч отбрасывается; из остального динамическим программированием
  выбирается одна непротиворечивая цепочка. В коротких разрывах положение
  оценивается по прямой и помечается «оценка», в длинных мяч — «неизвестно».
  На игровом ролике: мяч найден на 33 % кадров, известен (с оценкой) на 52 %;
  по выборочной ручной проверке ~85–90 % найденных позиций — действительно
  игровой мяч. Остальное время мяч закрыт ногами в борьбе или слишком мелкий —
  это ограничение съёмки 720p с бровки, а не алгоритма.
* **Тактическая доска** (`board.py`, панель рядом с видео): все найденные
  игроки, мяч и игрок в фокусе на схеме поля, синхронно с видео, со следами
  перемещений за 3/8/20 с. Команды — кластеры цвета формы по трекам (две самые
  «людные» группы на поле — команды, третья — судья/тренеры/вратарь), «свои» —
  команда игрока в фокусе; цвет точки — реальный цвет формы. Мяч найденный —
  белая точка, оценённый — пунктирный кружок.
* **Схема поля подгоняется по игрокам** (`pitch.fit_to_occupancy`). Глубина от камеры считается по росту
  в кадре и зависит от неизвестного зума телефона: на игровом ролике она была растянута в ~1.6 раза, и
  35–39 % положений игроков оказывались за полем. За матч дети покрывают почти всё поле, поэтому масштабы
  вглубь и поперёк и положение камеры подбираются так, чтобы облако положений детей-участников (без
  взрослых и выключенных) легло в поле формата. Направление взгляда и свои ворота — из отметок оператора;
  без отметок — камера у длинной бровки, поле по формату (6×6 — 45×30 м). Итог: за полем 3 % положений.
  Если снята только часть поля, камера по этой оси не сдвигается. Подгонка применяется к доске, мячу
  (граница поля) и разделу «На поле» в метриках; выключение людей её уточняет.
* **Разметка поверх видео.** Плеер показывает чистую копию кадров (`frames.mp4`), а рамки и номера рисуются
  слоем поверх, синхронно с кадром (`GET /api/jobs/{id}/tracks` — рамки всех треков по кадрам): цель —
  ярко-зелёная, выбранный — ярко-красный с подсветкой, свои — прозрачно-красные, соперник — прозрачно-белые,
  взрослые и не определённые — серо-голубые, выключенные — серые пунктирные. Цвета меняются сразу после
  пометок, без перерисовки видео; `annotated.mp4` с впечатанной разметкой остаётся для скачивания.
  Щелчок по красной зоне ленты ставит видео на паузу ровно на первом кадре потери цели (на ленте
  несколько кадров на пиксель — щелчок «примагничивается» к ближайшей потере).
* **Кто играет — решает оператор.** Выбор в два щелчка — на доске или прямо по рамке на видео: первый
  выделяет человека (красное кольцо на доске, красная рамка на видео, подсказка с кнопками «Выключить» /
  «Отмена»), второй выключает (или возвращает выключенного). Щелчок мимо снимает выделение. На доске видны все найденные люди, включая стоящих у бровки и за
  полем (они прижимаются к краю схемы пунктирным кружком). У каждого — короткий номер (1, 2, 3… по порядку
  появления, `board.display_numbers`): тот же номер подписан над рамкой на видео. Клик по точке выключает
  человека (запасной, тренер, зритель), галочка «показать выключенных» показывает их бледно — клик
  возвращает; метки под доской тоже возвращают. Выключенные не участвуют в метриках («ближайший игрок»,
  единоборства), игровом контексте и ИИ-разборе. Пометка хранится с началом трека (кадр + рамка), поэтому
  после поправки цели, когда треки перенумеровываются, она остаётся на том же человеке. Автоматическое
  правило «вне игры» (`board.classify_roles`) ошибалось на реальном ролике и выключено
  (`BoardConfig.auto_roles`). Номера одного человека могут меняться, если его трек рвался (перекрытие,
  уход из кадра) — тогда у него на ролике несколько номеров.
* **Команды и вратари.** Взрослые (судья, тренеры, зрители) отсекаются по росту: рамка выше
  ожидаемого роста ребёнка в этой точке земли на ≥ 12 % (у детей 0.84–1.06, у взрослых 1.17–1.33 на
  игровом ролике). Оставшиеся дети делятся на две команды по цвету формы; если формы не различимы,
  команды не назначаются и причина показывается под доской. Вратарь узнаётся по положению (у одной
  линии ворот, в створе, далеко от места игры, с малым разбросом, один на ворота) и получает команду
  по стороне ворот — его форма другого цвета кластеризацию не портит; на доске он с кольцом цвета
  команды.
* **Игровой контекст для метрик и ИИ** (`board.game_context`): где мяч по
  третям, у кого он (владение с гистерезисом: ближайший игрок в 2 м + 5 % глубины, смена владельца —
  только если другой ближе на 1 м полсекунды; отрезки владения считаются), расстояние
  игрока до мяча, его положение относительно центра своей команды и её
  последней линии. Всё это попадает в посекундную ленту, раздел `game`
  метрик и в инструменты ИИ-разбора (включая расстановку на момент времени).

Положение игрока в фокусе на поле (раздел «На поле», лента, тепловая карта поля) считается по той же
плоскости поля, что и доска, — по строке ног, а не по росту рамки: частично закрытый игрок иначе
«улетал» бы вглубь на метры (расхождение доски и ленты на игровом ролике: 90-й процентиль 1.6 м
вместо 6 м). Скорости и дистанция по-прежнему по росту.

Повторная детекция мяча в разрывах цепочки вокруг предсказанного положения (`ball_roi`) есть, но
выключена по умолчанию: на игровом ролике она добавила мяч лишь на 23 кадрах из 976 разрывов — в
разрыве мяч почти никогда не там, где предсказано (разрыв возникает как раз при ударе).

**Прогон в два этапа.** Этап 1 — слежение без поиска мяча на плитках (~10 кадр/с на Mac M-серии вместо
~2): задача сразу получает статус «готово», видео с номерами, доска, метрики и разбор по игрокам уже
доступны. Этап 2 идёт в фоне (строка прогресса «мяч ищется в фоне: N/M кадров», ~3 кадр/с): мяч
ищется на увеличенных плитках по сохранённой копии кадров, затем доска и метрики пересчитываются
с мячом, страница обновляется сама. Пока идёт этап 2, доска и метрики честно пишут «мяч ещё ищется».
Этапы 2 разных задач идут по одному (делят GPU); прерванный перезапуском сервера этап продолжается при
старте; поправки цели во время поиска мяча не мешают — перестроение подхватит найденный мяч. Замер на
игровом ролике (450 кадров): этап 1 — 45 с с записью видео, этап 2 — ещё 150 с.

Доска и мяч считаются по сохранённым данным прогона. Для задач, прогнанных
раньше, в панели доски есть кнопка «Построить доску»: слежение перестраивается
по `inputs.npz`, а мяч ищется заново по копии кадров (несколько минут, один раз).

### Состав: кто в игре

Пометка относится к **человеку**, а не к номеру трека: трекер рвёт человека на фрагменты (зашёл за другого, камера ушла
и вернулась), поэтому выключенный человек остаётся выключенным во всех своих фрагментах, а похожие на него по внешности
(тот же зритель через минуту) выключаются следом. Под доской видно, сколько фрагментов выключено «тот же человек» и
«похожи по внешности»; любую ошибку исправляет щелчок по человеку.

- Лучший способ: поставить на паузу кадр, где видно побольше лишних (тренеры, зрители, запасные), и выключить **всех** —
  остальные люди этого кадра становятся примерами «играет». Второй такой кадр из другой части ролика заметно повышает точность.
- Щелчки применяются сразу, доска и метрики пересчитываются один раз, когда щелчки стихли.
- Режим «В игре: только отмеченные мной (и похожие на них)» — обратная логика: отмечаете игроков, остальные вне игры.
- Замена: выберите человека и нажмите «Ушёл с поля — с этого момента» / «Вышел на поле — с этого момента».
- Цель слежения выключается только явной пометкой. «Снять все пометки» — под доской.

### Разметка поля на кадре

Если разметка площадки кривая или камера стоит так, что поле плохо видно, отметьте поле сами — блок «Поле на видео».

1. Поставьте видео на кадр, где площадку видно лучше всего, нажмите «Отметить на текущем кадре».
2. Редактор сразу ставит точки вокруг места, где за ролик двигались игроки (голубые точки — «где играли»). Это заготовка.
3. Два режима («Что отмечаю»):
   - **четыре угла поля** — точки 1–4 в углах (1 — левый ближний, дальше по кругу); угол за краем кадра ставится в серой зоне;
   - **два дальних угла + боковые линии** — когда камера у бровки и ближние углы далеко за кадром: 3 и 4 — дальние углы,
     1 и 2 — любые видимые места на боковых линиях. Остальное достраивается по модели камеры; редактор пишет, насколько
     точки с ней согласуются (в метрах).
4. Точная доводка: лупа при перетаскивании, стрелки клавиатуры (Shift — по 10 px), масштаб − / +, «На весь экран».
5. Свои ворота — щелчком по воротам на кадре. «Раздвинуть по игрокам» переносит только те стороны, за которые игроки выходят.
6. После сохранения: «за границей поля N % положений» (ориентир качества), четыре кадра из разных мест ролика с линиями —
   если линии где-то сползли (оператор перешёл), откройте тот кадр и отметьте поле ещё раз: разметок может быть несколько,
   каждый кадр считается по ближайшей по времени.
7. Под доской появляется «Похоже, не играют» — люди, которые почти всё время стоят за границей отмеченного поля;
   выключить их можно одним щелчком.

Точность переноса разметки между кадрами даёт фоновая привязка кадров к сцене (`tracker/camreg.py`, 0.5–1 мин на ролик,
считается сама после слежения): сползание линий 1–3 px вместо 15–25 px. Замеры и ограничения — `FIELD_TEST_2026-09-17.md`.

## Видео с iPhone 15 Pro Max

`tracker/video.py` читает ролик через ffmpeg (бинарник из `imageio-ffmpeg`),
потому что «как есть» ролики iPhone ломают наивное чтение:

| Особенность | Что делаем |
|---|---|
| HEVC (H.265) в `.MOV` | ffmpeg декодирует; OpenCV из pip часто без HEVC |
| HDR Dolby Vision (10 бит, HLG `arib-std-b67` / PQ) | тонмаппинг в BT.709 (`zscale`+`tonemap=hable`), иначе цвета формы «плывут» и команды не разделяются; при отказе фильтра — откат с предупреждением |
| Поворот в метаданных | ffmpeg поворачивает сам; `probe()` отдаёт размер уже после поворота |
| Переменная частота кадров (VFR) | `-fps_mode cfr`: кадр = 1/fps, номера кадров совпадают с временем |
| 4K 60 fps | `--width 1280`: детекция на уменьшенной копии, рамки масштабируются обратно |
| ProRes Log | тонмаппинг не применяется; нужен LUT — лучше снимать без Log |

**Рекомендации по съёмке** (снимают нагрузку с алгоритма):

* 4K 30 fps или 1080p 60 fps; 60 fps даёт мультитрекеру вдвое больше опор
  при столкновениях. 240 fps слоу-мо не нужно.
* **Выключить HDR-видео** (Настройки → Камера → Запись видео → HDR-видео) —
  8-битный SDR с BT.709, тонмаппинг не нужен, цвета стабильны.
* Заблокировать экспозицию/фокус (долгое нажатие в приложении Камера):
  автоэкспозиция при пробеге игрока на фоне неба меняет цвет формы.
* Основная камера 24 мм / 48 мм (телеобъектив 120 мм с рук дрожит), без
  «Режима действия» (он кропит и портит края).
* Точка съёмки — сбоку и повыше (трибуна, штатив с площадкой), панорамировать
  плавно, штатив/монопод. Держать целевого игрока в кадре не обязательно —
  для этого и есть повторный захват — но чем меньше перекрытий, тем лучше.
* Если игрока снимают специально: зафиксировать номер (`--number`), это
  главный признак против одноклубников.

рук панорамирует на ~90 px. Цель — игрок в розовой манишке; в кадре ещё

стоит в очереди полностью закрытая игроками, затем проходит упражнение второй

|---|---|

Оставшиеся ошибки: перекрытие с соседом, в котором мультитрекер переносит id

подобраны на одном ролике: на новых съёмках первым делом размечать и
смотреть `accuracy`.

## Ограничения

* Два игрока одной команды, у которых **не видно номера** и совпадают волосы,
  цвет кожи и бутсы, различаются только движением — после долгой потери
  алгоритм честно отвечает `ambiguous` и ждёт ручного выбора.
* Цветовой дескриптор чувствителен к освещению (тень/солнце): галерея с
  разных ракурсов и калибровка это сглаживают, но OSNet (`--encoder osnet`)
  заметно устойчивее.
* OCR номеров на CPU дорог: читается только цель раз в `number_every` кадров
  и до `number_max_candidates` кандидатов при поиске.

## На самом iPhone (on-device)

Та же архитектура переносится на iOS без изменений логики:

* детектор — YOLO, экспортированный в CoreML (`yolo export format=coreml`),
  или `VNDetectHumanRectanglesRequest` из Vision;
* дескриптор — цветовые гистограммы по полосам считаются на CPU/Metal, OSNet
  экспортируется в CoreML;
* `KalmanBoxFilter`, `MultiTracker`, `TargetFollower` — чистая арифметика
  над рамками и векторами (numpy → Accelerate/vDSP или простые массивы);
  порядок и пороги в `TargetConfig` переносятся как есть;
* кадры — `AVCaptureVideoDataOutput` в BGRA, 30 fps, 1080p; HDR отключается
  через `videoHDREnabled = false`, поворот — `videoOrientation`;
* номер — `VNRecognizeTextRequest` (accurate, только цифры) на вырезке торса.

Python-версия — эталон: её `track.json` на том же ролике служит проверкой
портированной логики.

## Тесты

```sh
cd player_tracker && python -m pytest tests/ -q
```

Нейросети в тестах не нужны: детекции задаются сценарием, дескрипторы —
синтетические векторы или рисованные «игроки». Покрытые сценарии:

* уход цели из кадра при присутствии одноклубника с похожим дескриптором —
  ложного захвата нет, возвращение под новым id ловится за <10 кадров;
* два неразличимых кандидата без номера → `ambiguous`, а не захват;
* прочитанный номер снимает неоднозначность за несколько кадров;
* чужой номер на треке цели → `released_number`; чужая команда → отказ;
* подмена id при столкновении → `released_swap` и повторный захват верного трека;
* краткий пропуск детекций → повторный захват за 1 кадр по непрерывности;
* мультитрекер: пересечение двух игроков с сохранением id, слабые детекции,
  выживание при пропусках, удаление по таймауту;
* декодирование через ffmpeg с уменьшением и фрагментом, откат на OpenCV;
* сквозной прогон на рисованных кадрах: уход за край, возвращение, экспорт;
* метрики: эпизоды потерь, схлопывание серий в журнале, оценка по разметке
  (TP/wrong/missed/false_track, смены id), исключение детектора не роняет
  прогон и попадает в журнал;
* компенсация камеры: оценка сдвига по фону с маской игроков, откат на
  тождество, трек не рвётся при панорамировании шире рамки;
* «сосед»-двойник не захватывается; цель, скрывшаяся посреди кадра, не
  «телепортируется» к двойнику на другом краю; голоса команды прежнего
  владельца id забываются; при многоцветных манишках команды не определяются;
* уточнение: задержка захвата убирается, поздняя подмена id обрезается,
  короткий разрыв интерполируется с учётом движения камеры;
* клик по слабо детектированному игроку вплотную к соседу — захват в кадре выбора;
* миниатюра различает раскладку цвета, которую не видят гистограммы;
* оценка с `partial`/`hidden` и `accuracy`;
* веб-API: загрузка ролика, кадр для выбора, полный цикл задачи с файлами,
  оценка по разметке, валидация, не найденная цель, отмена, состояние после
  перезапуска (сценарный детектор вместо YOLO).

```
player_tracker/
├── track.py               # CLI
├── serve.py               # веб-приложение (FastAPI + uvicorn)
├── webapp/
│   ├── server.py          # API и раздача фронтенда
│   ├── jobs.py            # задачи в фоне, хранилище data/, оценка по разметке
│   └── static/            # index.html, app.js, style.css — без сборки
├── tracker/
│   ├── video.py           # ffmpeg: HEVC, HDR-тонмаппинг, поворот, VFR, масштаб, запись H.264
│   ├── detection.py       # YOLO (ultralytics) + сценарный детектор для тестов
│   ├── camera.py          # компенсация движения камеры (оптический поток по фону)
│   ├── appearance.py      # полосовые HSV-гистограммы, миниатюра фигуры, OSNet (опц.)
│   ├── jersey.py          # OCR номера (easyocr, опц.) и накопитель голосов
│   ├── team.py            # k-means по цвету торса: команда A / B / прочие
│   ├── kalman.py          # фильтр Калмана (cx, cy, a, h)
│   ├── multitracker.py    # ByteTrack + внешность + строб Махаланобиса
│   ├── target.py          # модель цели и автомат ACTIVE/CONTESTED/LOST
│   ├── offline.py         # журнал мультитрекера и уточнение результата по всему ролику
│   ├── player_metrics.py  # метрики игрока в метрах по росту в кадре: дистанция, зоны, спринты, мяч рядом
│   ├── analyst.py         # ИИ-разбор (DeepSeek): выжимка данных, инструменты, правила
│   ├── profile.py         # опрос об игроке: возраст → зоны скорости и рост, позиция, формат → ориентиры
│   ├── pitch.py           # схема поля: камера, взгляд, свои ворота -> метры поля, трети, фланги, направления
│   ├── ground.py          # плоскость поля по рамкам людей: глубина точки земли и ожидаемый размер мяча
│   ├── ball.py            # игровой мяч по всему ролику: кандидаты -> треклеты -> цепочка, запасные мячи
│   ├── board.py           # тактическая доска: все игроки, команды по цвету формы, мяч, игровой контекст
│   ├── pipeline.py        # склейка, выбор цели, политика OCR
│   ├── render.py          # отрисовка
│   ├── export.py          # JSON/CSV/события/сводка
│   └── metrics.py         # метрики прогона, журнал ошибок, оценка по разметке
└── tests/                 # pytest, без нейросетей
```
