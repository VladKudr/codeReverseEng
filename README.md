# req-reverse v3 — обратная разработка требований из кода

Пайплайн восстанавливает требования из исходного кода: дешёвые LLM извлекают
факты по жёстким схемам, дорогая модель синтезирует, валидация сверяет
требования с кодом. v3 разделяет пайплайн на два слоя:

1. **Детерминированный слой (Python)** — оркестрация, схемная валидация,
   механические проверки, отчёты. Всё, что решается grep'ом, диффом и
   пересчётом, выполняет код, а не модель.
2. **Смысловой слой (промпты)** — извлечение правил и домена, синтез,
   формулировки. Промпты v2, похудевшие на механику.

Паттерн: **LLM порождает → код проверяет → LLM правит по тексту конкретной
ошибки.** Гейт — всегда код. Ретраи ограничены (2), затем эскалация человеку.

Граница слоёв: задача уходит в код, если ответ можно получить механически
(поиск подстроки, сравнение чисел, обход дерева, regex); задача остаётся LLM,
если требует чтения смысла кода.

## Состав

```
req-reverse/
├── runner.py              # оркестратор: этапы, фан-аут по модулям, ретраи
├── config.yaml            # пути, команда CLI-агента, пороги, модель по этапам
├── schemas/               # JSON Schema каждого типа артефакта (этапы 0–4, 90)
├── checks/                # механические проверки (каждая — отдельный модуль)
│   ├── schema_check.py        # схемная валидация с ошибками retry-формата
│   ├── evidence_binding.py    # слой 1: цитата дословно в файле ±3 строки
│   ├── id_allocator.py        # выдача свободных диапазонов ID
│   ├── completeness.py        # пересчёт полноты: правила ↔ истории ↔ трассировка
│   ├── coverage.py            # покрытие ветвлений: raise/if/match без правил
│   ├── inverse_match.py       # этап 92: сверка предсказаний кода с фактом
│   └── secrets_mask.py        # маскирование секретов в evidence
├── prompts/               # промпты v2, похудевшие на механику + RUNBOOK.md
├── templates/             # шаблоны SRS, историй, матрицы трассировки
├── reports/               # шаблоны сводных отчётов прогона
└── tests/                 # pytest; фикстуры — реальные исходники tenacity
```

## Запуск

```sh
# зависимости: Python >= 3.10, pyyaml, jsonschema (тяжёлых фреймворков нет —
# комплект запускается в закрытом контуре)
pip install pyyaml jsonschema

# 1. заполните config.yaml: repo.path (корень анализируемого репозитория),
#    repo.name, workspace и agent.command — команду ВАШЕГО CLI-агента.
#    Комплект не привязан к конкретному LLM/CLI: промпт передаётся через
#    {prompt_text}, {prompt_file} или stdin, модель этапа — через {model};
#    прямых обращений к API в коде нет. Рецепты под конкретные инструменты —
#    prompts/RUNBOOK.md, раздел «Настройка CLI-агента».
# 2. прогон:
python runner.py --config config.yaml     # этапы 0–7 и 90
```

Подробности — `prompts/RUNBOOK.md`. Повторный запуск идемпотентен: этапы с
валидным выходом пропускаются (`--force` — перегенерация).

**Ярусная глубина** (`config.yaml → tiers`): `L0` — этапы 0–1 («оглавление»
по всему ландшафту), `L1` — + 2–3 (зоны интеграций), `L2` — полный прогон
(горячие capability). Умолчание вне карты — `L0`; без секции `tiers` всё идёт
как `L2`. Холодная зона поднимается по требованию:
`python runner.py --raise-tier <путь> L2` — недостающие этапы догоняются,
готовые артефакты нижних ярусов не перегенерируются.

**Инверсная верификация** (`config.yaml → validation.inverse: true`, этап 92):
для систем, где исполнение (слой 2) недоступно. Модель видит только
`statement`'ы правил (без evidence/source) и предсказывает код; предсказания
механически сверяются с исходниками (`checks/inverse_match.py`). Низкая доля
по правилу — из формулировки не восстанавливается поведение, кандидат на
возврат в этап 4. Пороги в v3 не калибруются — только статистика в
`workspace/reports/inverse_match.md`.

## Что проверяет детерминированный слой

| Проверка | Когда | Что ловит |
|---|---|---|
| JSON Schema (`schemas/`) | после каждого этапа 0–4, 90 | битые/неполные артефакты; ошибки уходят в retry-промпт с путём до поля |
| `evidence_binding` | после каждого этапа 4 и перед 90 | выдуманные ссылки, сокращённые цитаты, неверный `enclosing` (AST для Python, эвристика для прочих языков — помечается) |
| `id_allocator` | до этапа 4 (выдача блока) и после (коллизии) | два модуля с одинаковыми R-101…R-104 |
| `completeness` | после этапа 7 | правило без строки в покрытии историй; уникальные `rule_id` ≠ N; самодельные колонки трассировки |
| `secrets_mask` | сразу после записи каждого артефакта | пароли, токены, строки подключения, приватные ключи в `evidence` → `***MASKED***` с записью в журнал |
| `coverage` | конец прогона | доля веток `raise`/`if`/`match` без правил; функции без единого правила |
| `inverse_match` | после этапа 92 (если включён) | предсказания, не восстановимые из формулировок: доля подтверждённых по каждому правилу |

Сводка прогона (`workspace/run_summary.md`) показывает и **точность**
(этап 90), и **полноту** (coverage), плюс ретраи, эскалации и стоимость по
токенам, если агент отдаёт метрики.

## Проверено на живых прогонах (v2)

| Проект | Требований | Подтверждено |
|---|---|---|
| `simonw/sqlite-utils` | 34 | 34/34 = 100% |
| `jd/tenacity` (Kimi CLI) | 129 | 128/129 = 99.2% |

Каждое правило в промптах закалено реальным провалом; в v3 механические уроки
перенесены в код (см. таблицу в `prompts/RUNBOOK.md`).

## Тесты

```sh
cd req-reverse && python -m pytest tests/ -q
```

Артефакты реальных прогонов (workspace/) в архив v2 не вошли, поэтому фикстуры
строятся на **настоящих исходниках tenacity 9.1.4** (`tests/fixtures/tenacity/`,
те же шесть модулей, что в прогоне Kimi; лицензия Apache-2.0 приложена) и
воспроизводят известные сценарии:

* сокращённая цитата docstring — 1 из 145, без ложных срабатываний на
  остальных 144 (`test_evidence_binding.py`);
* коллизия R-101…R-104 двух «параллельных» модулей (`test_id_allocator.py`);
* подсаженные строка подключения, токен и приватный ключ
  (`test_secrets_mask.py`);
* расхождение счёта правил и трассировки (`test_completeness.py`);
* воспроизводимые числа покрытия (`test_coverage.py`);
* полный цикл runner'а на мини-репозитории с мок-агентом: план, ретраи,
  эскалация, идемпотентность (`test_runner.py`);
* ярусы: фильтр плана по карте, `--raise-tier` без перегенерации (`test_tiers.py`);
* этап 92: зафиксированный LLM-выход как фикстура, воспроизводимый отчёт
  `inverse_match`, выключение флагом (`test_inverse.py`).

Для прогона на реальных данных укажите в `config.yaml` пути к вашему
репозиторию и workspace.
